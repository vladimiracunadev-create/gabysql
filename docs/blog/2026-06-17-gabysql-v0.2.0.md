# gabysql v0.2.0 — Build log de un motor SQL en Rust desde cero

*Publicado: 2026-06-17 · Autor: [@vladimiracunadev-create](https://github.com/vladimiracunadev-create) · [Repo](https://github.com/vladimiracunadev-create/gabysql) · [Release](https://github.com/vladimiracunadev-create/gabysql/releases/tag/v0.2.0)*

---

## TL;DR

Construí desde cero un motor SQL relacional embebido en Rust. **0 líneas de C** en el core. WAL + B+Tree real + CRC32 por página. La superficie SQL cubre DDL+DML+TCL+PL/pgSQL+RLS+CTEs+window functions+SAVEPOINT+sessions HTTP cross-request.

**Marcadores objetivos al cierre de v0.2.0**:
- **828 tests verdes** (incluyendo 3 redes property-based hand-rolled sobre planner / Pager / parser).
- **1 hora de fuzz limpio** sobre el parser: 503 861 946 queries random, 0 panics, seed reproducible.
- **90 ADRs** documentando cada decisión de diseño.
- VERSION on-disk 33 estable; CI verde en Ubuntu/macOS/Windows + Docker + bench job.

**No es** un producto comercial. Es un proyecto de aprendizaje + exploración. Pero llegó a un estado donde otros pueden mirarlo y aprender de las decisiones, así que lo publico.

---

## Por qué otro motor SQL

Tres respuestas honestas:

1. **Quería entender bases de datos a fondo.** Leer libros sobre Pager/B+Tree/WAL me daba intuiciones falsas. Implementarlas obliga a confrontar cada simplificación que uno hace al leer.

2. **Curiosidad por el supply chain.** SQLite es ~150 000 líneas de C. PostgreSQL son millones. Quería ver qué pasa si construyo el equivalente operativo en Rust puro — sin `libc`, sin `cc-rs` levantando código de terceros, sin nada que uno pueda olvidar revisar.

3. **Una pregunta de diseño abierta**: ¿cómo se vería un motor pensado para que el cliente principal no sea un humano escribiendo SQL ni una app convencional, sino un agente LLM razonando sobre datos? Acá hay un hilo conductor que sigo siguiendo en [AGENDA_INVESTIGACION.md](../AGENDA_INVESTIGACION.md).

## Lo que aprendí construyendo (cosas que me hubieran ahorrado meses si las hubiera sabido antes)

### 1. El B+Tree es la mitad fácil. El WAL es la mitad real.

Tenés ahí explicado un B+Tree en cualquier libro de algoritmos. Lo difícil no es el árbol — es el momento en que tres páginas dirty conviven con un commit que se interrumpió a la mitad, y vos tenés que poder reabrir el archivo después y decir con confianza qué pasó.

Mi WAL es after-image (escribo la versión post-cambio de cada página, no el undo log). Replay es trivial; rollback es "dropear el WAL y re-leer page 0". Lo que se vuelve sutil son los corner cases:

- ¿Qué pasa si el `fsync` del WAL volvió OK pero el del `.db` no llegó a disco?
- ¿Y si el WAL está corrupto en la página 17 de 50? ¿Aplico hasta la 16 o abortás?
- ¿Y si el lector ve el header con un `commit_marker` que el writer todavía no flusheó?

La respuesta no es "el código correcto" — es **3 crash tests dirigidos + un property test sobre secuencias random de begin/insert/commit/rollback que verifica `INTEGRITY CHECK` post-mortem**. Eso fue lo único que me dejó dormir tranquilo.

### 2. El parser es donde van a aparecer todos los crashes que nadie buscó.

`unwrap()` que parecían inofensivos resultaron disparables con queries que el grammar formal "no acepta" pero que llegan igual porque el tokenizer tropezó. La forma de no engañarse es **fuzzear durante una hora limpia** y ver.

Mi fuzz parser es hand-rolled (libFuzzer choca con Windows + GNU toolchain + zero-deps). Genera 70% queries pseudo-estructuradas con vocabulario SQL real y 30% mutación adversarial de bytes random. **1 hora limpia = 503.8M iters @ 139k iters/seg, 0 panics**. Evidencia capturada en [docs/fuzz/FUZZ-RUN-2026-06-15.md](../fuzz/FUZZ-RUN-2026-06-15.md) con seed determinístico para reproducir.

Antes del fuzz tenía 23 panic-able edge cases que no había encontrado con tests dirigidos. Después del fuzz tengo 0 conocidos. No es lo mismo "no encontré bugs" que "0 bugs en 500 millones de inputs".

### 3. El planner cost-based te miente si no lo testás con property tests.

Cuando agregué un `INDEX_BREAKEVEN_SELECTIVITY` que decide cuándo el FullScan es más barato que el lookup indexado, me di cuenta de algo incómodo: **una constante mal puesta cambia silenciosamente el plan** sin cambiar el resultado. Si la query devuelve los mismos rows, todos mis tests pasaban verdes, pero el motor estaba eligiendo el path lento.

Lo que defiende contra esto no son más tests unitarios. Es:

```rust
// Para CUALQUIER dato y CUALQUIER WHERE, el resultado de un SELECT
// debe ser idéntico con/sin ANALYZE corrido. Si no, el planner mintió.
fn proptest_select_results_invariant_with_vs_without_analyze() {
    for run in 0..50 {
        let seed = lcg.next();
        let db_no_stats = populate(seed, 100);
        let db_stats = populate(seed, 100);  // misma data, mismo seed
        analyze(&db_stats);

        for q in 0..3 {
            let w = random_where(seed ^ q);
            let res_a = SELECT id FROM t WHERE w ORDER BY id;
            let res_b = SELECT id FROM t WHERE w ORDER BY id;  // con stats
            assert_eq!(res_a, res_b);  // mismo SET o el planner rompió correctness
        }
    }
}
```

240 comparaciones automáticas por corrida sobre el planner. Misma técnica replicada sobre el Pager (commit visibility / rollback discards / chained tx integrity). **3 redes property-based zero-deps**, todas con seed reproducible. Si una falla, imprime el seed y reproducís el caso 1:1.

Esto fue lo que me cambió la confianza de "creo que el optimizer está bien" a "tengo evidencia de que cualquier WHERE random sigue siendo correcto".

### 4. SAVEPOINT vale más de lo que parece.

Cualquier ORM moderno (SQLAlchemy, Hibernate, Diesel) asume **`SAVEPOINT` + `ROLLBACK TO SAVEPOINT` + `RELEASE SAVEPOINT`** disponibles. Sin eso, no podés hacer "intento N inserts, si uno falla revierto solo ese". Tirás los 50 inserts y empezás de nuevo.

Implementarlo no es complicado conceptualmente — snapshot del cache + header en cada savepoint, restore en el rollback — pero te obliga a pensar bien la semántica ANSI:

- ¿Releasear un savepoint revierte? **No.** Solo lo saca de la stack.
- ¿Rollback to deja el savepoint disponible? **Sí.** Hay que `RELEASE` después.
- ¿Re-savepoint con el mismo nombre? **Marca un nuevo punto sin borrar el anterior.**

Tres detalles que si los hacés mal, el ORM que confió en tu implementación de SAVEPOINT te va a dar resultados raros 6 meses después.

### 5. Cross-request HTTP transactions: la diferencia entre "embebido" y "usable como server".

Esta fue la última pieza. Antes de M13, cada request al server HTTP abría un Pager nuevo, hacía `begin/exec/commit/close` y lo cerraba. Un cliente que mandaba `BEGIN; INSERT (1);` en un request y `INSERT (2); COMMIT;` en otro no veía continuidad — la primera transacción ya estaba commiteada cuando el segundo request llegaba.

Para que un ORM lo use vía HTTP necesitás **sesiones cross-request**: el cliente abre una con `POST /tx/begin`, recibe un `session_id`, lo manda en cada `POST /exec` (header `X-Gabysql-Session: <hex>`), y cierra con `POST /tx/commit` o `POST /tx/rollback`. El server mantiene el Pager vivo entre requests.

Yo lo implementé como **single-slot global** (una sesión activa a la vez en todo el server) porque la concurrencia real depende de WAL-mode y eso queda para más adelante. Pero esa decisión es 100% suficiente para el caso target (ORMs que serializan a "una connection").

**Backwards compatible**: requests sin session header funcionan idénticos a antes. Cero migración para clientes existentes.

## Lo que NO hice

Por honestidad, no por modestia:

- **No es un motor de producción.** No tiene usuarios. No tiene tracking de regresiones contra una baseline. No tiene corridas en Postgres-level de carga real. Sería irresponsable poner esto debajo de algo crítico.
- **No tiene MVCC ni multi-writer.** Single-writer estricto. Si querés ese paradigma → Postgres.
- **No tiene wire protocol compatible con Postgres/MySQL.** Hablás HTTP/JSON o usás el crate embebido. No hay driver psql.
- **No es OLAP.** Row-oriented, sin compresión columnar. DuckDB existe.

## Quickstart si te interesa probarlo

```bash
# Instalar (Windows, no necesita admin):
iwr https://raw.githubusercontent.com/vladimiracunadev-create/gabysql/main/scripts/install.ps1 | iex

# O bajar binario de Linux/macOS/Windows:
# https://github.com/vladimiracunadev-create/gabysql/releases/tag/v0.2.0

# Crear una DB y meter datos:
gabysql init demo.db
gabysql exec demo.db "CREATE TABLE users (id INT PRIMARY KEY, name TEXT NOT NULL);"
gabysql exec demo.db "INSERT INTO users VALUES (1, 'Ana');"

# Levantar el server HTTP:
gabysql-server -db demo.db -addr :8080

# Desde otra terminal: cross-request transactions vía sessions
SESSION=$(curl -sX POST http://localhost:8080/tx/begin -d '{}' | jq -r '.session')
curl -X POST http://localhost:8080/exec \
    -H "X-Gabysql-Session: $SESSION" \
    -d '{"sql":"INSERT INTO users VALUES (2, \"Beto\")"}'
curl -X POST "http://localhost:8080/tx/commit?session=$SESSION"
```

Cinco minutos, un binario, sin instalar nada más.
